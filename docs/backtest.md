# 백테스트 — 종목 선정 규칙을 과거에 돌려보기

> 상태: ✅ 구현 완료 (2026-09-21) · 데이터 수집은 서버에서만 동작

## 왜 만들었나

"당일 상승률 상위 10", "당일 거래대금 상위 10" 같은 단순한 종목 선정 규칙이 실제로 돈이 되는지
알고 싶은데, 실매매로 확인하려면 몇 달이 걸리고 그 사이 손실은 진짜 손실이다. 과거 캔들로 같은
규칙을 되돌려 보면 며칠 안에 답이 나온다.

핵심 질문은 두 개다. **종목 선정이 먹히는가**, 그리고 **지금 쓰는 청산 로직이 보탬이 되는가**.
둘은 따로 답해야 한다 — 상위 10을 샀더니 수익이 났다고 해서 그게 선정 덕인지 청산 덕인지는 하나만
봐서는 모른다. 그래서 같은 종목 선정에 "현재 청산 로직"과 "기준선(정해진 시간만 보유 후 청산)"을
나란히 돌려 비교한다(`--compare`).

## 로직을 새로 만들지 않았다

`app/core/trade_strategy.py`의 `evaluate_entries()` / `evaluate_exits()`를 그대로 호출한다.
이 함수들이 시세를 `get_price_fn` 콜백으로 받는 순수 함수라, 콜백만 과거 캔들로 바꿔 끼우면 실거래에서
도는 판단 코드가 그대로 과거 위에서 돈다 — 목표 익절, RSI 과매수 매도, 트레일링 손절, 고점 대비
되돌림 익절, 회복형 분할 물타기까지 전부 같은 코드다. 백테스트용으로 따로 베낀 로직이 원본과
어긋나는 흔한 사고가 애초에 생기지 않는다.

성과 집계도 `app/core/trade_performance.py`의 `build_performance()`를 그대로 쓴다. 백테스트가
체결 기록을 `trade_order_log`와 같은 모양의 dict로 남기기 때문에 가능한 일이고, 덕분에 승률·손익비·
청산사유별 기여가 매매 성과 화면과 **같은 정의**로 나온다. 화면에서 보던 숫자와 바로 견줄 수 있다.

기존 코드에 더한 것은 세 곳뿐이다.

| 파일 | 변경 | 이유 |
|---|---|---|
| `trade_strategy.evaluate_exits()` | `now` 인자 추가 | 회복형 모드의 쿨다운/시간 하드스톱이 벽시계(`datetime.now()`)를 보면 과거를 돌릴 때 항상 "쿨다운 지남"으로 판정된다 |
| `trade_strategy.evaluate_entries()` | 후보의 `entry_reason`을 우선 사용 | 순위로 고른 후보가 스크리닝 신호 이름(`breakout_4h` 등)을 뒤집어쓰지 않게 |
| `trade_performance.normalize_exit_reason()` | `hold_period` / `backtest_end` 라벨 | 기준선과 구간 끝 정리가 리포트에서 '기타'로 뭉뚱그려지지 않게 |

## 미래를 당겨쓰지 않기 위한 규칙

백테스트에서 제일 흔한 사고가 look-ahead(미래 참조)다. 결과가 이상하게 좋으면 대개 여기가 새고 있다.

1. **순위는 "그 시각까지의" 데이터로만 계산한다.** 일봉만 보고 "그날 상승률 상위 10"을 고르면 장
   마감 뒤에야 알 수 있는 순위로 아침에 산 셈이 된다. 그래서 시각 T의 상승률은 *전일 종가 대비 T시점
   종가*, 거래대금은 *그날 KST 00시부터 T까지 누적분*이다. 업비트 화면의 정의와 같고 차이는
   "마감 기준이냐 진행 중이냐"뿐이다.
2. **체결가는 다음 봉의 시가다.** T의 종가를 보고 T의 종가에 사는 건 현실에 없는 체결이다.
3. **지표(RSI)도 T까지 확정된 봉만 본다.**

이 세 가지는 `tests/test_backtest_engine.py`가 매번 검증한다.

## 쓰는 법

### 1) 과거 캔들 모으기 — 서버에서만

```bash
python backtest.py collect --days 90 --interval minutes60
python backtest.py status        # 캐시에 뭐가 들어있는지
```

개발용 원격 세션에서는 업비트 API가 egress 정책으로 막혀 있어(CONNECT 403) 수집이 안 된다. 서버
(업비트 정상 접근)에서 돌려야 한다. KRW 280종목 × 1시간봉 90일이면 약 3,100회 호출, 초당 8회로 눌러
6~7분쯤 걸린다. 중간에 끊겨도 받은 만큼은 남고 다시 돌리면 빠진 구간만 채운다.

일봉은 항상 같이 받는다 — 업비트는 전일 종가(`prev_closing_price`)를 일봉에만 실어 주는데, 그게
없으면 "당일 상승률" 자체가 계산되지 않는다.

캐시는 `backtest_candles.db`에 쌓인다(운영 `alerts.db`와 분리 — 1시간봉 3개월이면 60만 행이고,
언제든 다시 받을 수 있는 파생 데이터라 날려도 된다).

### 2) 돌리기 — 캐시만 있으면 어디서든

```bash
# 상승률 상위 10 + 현재 청산 로직
python backtest.py run --selection gainers

# 선정 2종 × (현재 로직 / 기준선 24시간) 네 조합 한 번에 비교
python backtest.py run --compare

# 대시보드에 저장된 실제 매매 설정으로, 매일 9시에만 진입
python backtest.py run --from-db --entry-hour 9

# 파라미터 바꿔가며
python backtest.py run --take-profit 7 --stop-loss 3 --trailing-tp --min-trade-value 1000000000

# 짧은 손절 · 긴 수익 모드(docs/auto-trade-tight-stop.md) — 익절을 높게 둬야 수익이 안 잘린다
python backtest.py run --selection gainers --tight-stop --take-profit 30
```

`--from-db`를 주면 `app/config.py` 기본값 대신 대시보드에 저장된 설정으로 돌린다 —
"지금 내 설정으로 과거를 돌리면" 이 된다. `--json`으로 주문 내역과 자산 곡선까지 저장할 수 있다.

## 결과 읽는 법

- **수익률 / 최대낙폭(MDD)** — 계좌 자산 곡선 기준이다. 성과 화면의 MDD는 *청산된 사이클의 누적
  실현손익* 기준이라 아직 안 판 포지션의 하락을 못 보는데, 백테스트는 계좌가 얼마나 깊게 빠졌는지가
  중요하다(그게 실제로 못 버티고 끄게 되는 지점이다).
- **Profit Factor** — 총이익 ÷ 총손실. 1.0 미만이면 이긴 돈보다 잃은 돈이 많다. 승률이 높아도 이게
  1 미만이면 "자주 조금 벌고 가끔 크게 잃는" 모양이다.
- **청산 사유별** — 짧은 손절 · 긴 수익 모드는 `tight_stop_loss`(짧게 끊은 손실) /
  `tight_trail_exit`(트레일링으로 확정한 이익) / `tight_breakeven_exit`(본전에서 막은 건)으로 따로
  잡힌다. 이 모드는 승률보다 **손익비**로 읽어야 한다 — 자주 조금씩 끊기는 대신 이익 한 건이 커야
  합이 맞는 구조다. `take_profit`이 대부분이면 익절선이 낮아 먹을 걸 못 먹고 나오는 것일 수 있고,
  `stop_loss`가 압도적이면 진입이 늦다는 뜻이다. `backtest_end`는 구간 끝에 강제 정리된 건이라
  판단 근거로 쓰지 않는다.
- **기준선과의 차이** — 현재 청산 로직이 기준선보다 나쁘면, 그 종목 선정에는 이 청산이 안 맞는 것이다.

수수료는 업비트 0.05%(매수/매도)를 현금 원장에서 바로 뺀다. 모의매매 브로커는 수수료를 안 떼고
성과 화면이 나중에 추정치로 빼지만, 백테스트는 자산 곡선 자체가 결과물이라 원장에 반영하는 쪽이 맞다.

## 한계 — 결과를 믿을 때 같이 알아야 할 것

- **생존 편향.** 업비트 `/v1/market/all`은 지금 상장된 종목만 준다. 그때 급등했다가 상장폐지된
  코인은 순위에 아예 안 나온다. 결과가 실제보다 **좋게** 나오는 쪽으로 기운다.
- **호가·슬리피지 없음.** 다음 봉 시가에 원하는 수량이 전부 체결됐다고 가정한다. 거래대금이 적은
  종목은 실제로는 그 가격에 못 산다 — `--min-trade-value`로 걸러내는 게 그래서 있다.
- **봉 안쪽을 못 본다.** 1시간봉이면 그 한 시간 안에서 손절선을 찍고 되돌아온 움직임은 안 보인다.
  손절이 실제보다 덜 걸린 것으로 나온다. 더 촘촘히 보려면 `--interval minutes15`(데이터 4배).
- **한 구간의 결과는 한 구간의 결과다.** 3개월이 상승장이었으면 뭘 해도 벌었을 수 있다.
  기간을 나눠(`--from`/`--to`) 여러 구간에서 같은 결론이 나오는지 보는 게 안전하다.
- RSI 매도조건을 켜고 돌리려면 pandas가 필요하다(서버에는 설치돼 있다).
