# 서버 상태 점검 (`/api/health`)

## 왜 만들었나

수집·매매는 운영 서버에서만 돌고, 로컬 `alerts.db`·`app.log` 는 오래된 사본이다. "지금 서버가 제대로 돌고 있나"를
알려면 대시보드에 로그인해서 동기화 관리의 처리 로그와 로그 뷰어를 직접 봐야 했다.
이걸 한 번의 읽기 전용 호출로 모아, 매일 도는 자동 점검(Claude 예약 작업)이 서버 밖에서 볼 수 있게 한다.

저녁 요약(`stock_digest`)이 이미 스케줄 실패를 슬랙으로 보내지만, 그건 **봇이 살아 있을 때만** 온다.
봇 프로세스 자체가 멈추면 요약도 안 온다 — 밖에서 물어보는 쪽이 필요한 이유.

## 무엇을 보나

| 항목 | 내용 | 판정 |
|---|---|---|
| `freshness` | 수집 테이블별 마지막 저장 시각 | 24시간 수집은 90분 이내, 평일 수집은 "수집 시각+30분이 지난 평일엔 오늘 자료" |
| `jobs` | 최근 24시간 `job_run_log` 요약(`stock_digest.summarize_job_runs` 재사용) | 마지막 실행이 실패인 작업이 있거나 실행 기록이 0건이면 경고 |
| `log` | `app.log` 끝 512KB 에서 최근 24시간 ERROR/WARNING 건수와 최근 오류 20줄 | 실거래 주문 실패 줄(`실매수`/`실매도` 가 든 ERROR, `order_failure_count`)이 1건이라도 있으면 경고. 그 밖의 오류는 판정에 넣지 않음(읽고 판단) |

`overall` 은 `ok` / `warn` 둘 중 하나.

## 안전장치

- DB 를 `mode=ro` 로만 연다. 외부 API·매매 함수는 부르지 않는다.
- GET 전용. 토큰은 `/api/health` 한 경로에서만 통한다(다른 API 는 여전히 로그인 필요).
- 잔고·보유 종목·키 같은 값은 응답에 없다. 다만 로그 오류 줄이 그대로 나가므로 토큰은 비밀로 다룬다.

## 켜는 법

1. 서버와 점검하는 PC 의 `.env` 에 같은 값을 넣는다: `HEALTH_API_TOKEN=<길고 임의의 문자열>`
2. 서버는 API 프로세스를 다시 띄운다(`pm2 restart upbit-api`, 또는 다음 배포 때 자동).
3. `python check_health.py` — 종료 코드 0 정상 / 1 확인 필요 / 2 서버에 못 닿음·인증 실패.

토큰을 안 넣으면 로그인한 브라우저에서만 `/api/health` 를 볼 수 있다.

## 알고 남긴 한계

- **공휴일을 모른다.** 평일 휴장일엔 주식 수집 테이블이 `stale` 로 나온다(note 에 표시).
- **PM2 프로세스 목록은 안 본다.** 프로세스가 죽으면 수집이 밀리는 것으로 간접 확인한다. 실거래 봇은
  `job_run_log` 에 실행 기록이 남는 범위까지만 보인다.
- **서버 주소가 http 라 토큰이 평문으로 오간다.** 읽기 전용이라 피해 범위는 작지만, https 를 붙이면 없어지는 문제.
- 판정 기준(`health.FRESHNESS_RULES`)은 수집 코드의 시각을 보고 정한 첫 값이다. 실제로 돌려 보며 조정한다.
