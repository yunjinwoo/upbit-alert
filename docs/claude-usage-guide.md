# 클로드(Claude Code) 사용 가이드 — 이 프로젝트에서의 작업/리뷰 원칙

작업도 Claude가 하고 리뷰도 Claude가 하는 워크플로우를 쓰면서 정리해둔 원칙들. 실제로
`fix/lock-default-on` 브랜치에서 저장형 XSS를 하나 잡은 사례([docs/slack-login.md](slack-login.md) 관련
작업 중 발생)를 계기로 정리함.

## 1. "작업도 리뷰도 같은 모델"이 갖는 의미

- 코드를 쓸 때와 리뷰할 때는 프레임이 다르다. 구현 중엔 "기능을 동작하게 만드는" 모드고,
  리뷰는 "이 diff를 공격한다면 어디를 노리겠나"를 강제로 여러 관점(라인 스캔, 삭제된 안전장치
  추적, XSS 관점 등)으로 나눠서 보기 때문에 자기 자신이 쓴 코드에서도 실제로 문제를 잡아낸다.
  → 실제 사례: `templates/stock_memo.html`에 넣은 차트 패널 코드가 종목명을 이스케이프 없이
  `innerHTML`에 꽂아 넣는 저장형 XSS였는데, 구현 시점엔 못 잡고 `/code-review`에서 잡았음.
- 그렇다고 안심할 근거는 아니다. 같은 모델이 구조적으로 못 보는 종류의 실수는 리뷰에서도
  못 잡을 수 있다. 자기 자신을 검증하는 건 완전히 독립적인 사람 리뷰나 실제 침투 테스트를
  대체하지 못하는 "중간 단계 필터"로 취급할 것.
- 가장 확실한 검증은 리뷰가 "이럴 것 같다"고 말한 걸 **직접 재현**해보는 것. 이번에도 실제
  브라우저에서 payload를 넣어 XSS가 터지는 걸 확인하고, 수정 후 다시 넣어서 막히는 걸 확인하고
  나서야 확정했음.

## 2. `/code-review` vs `/code-review ultra`

| | `/code-review` | `/code-review ultra` |
|---|---|---|
| 실행 위치 | 지금 세션(로컬) | 클라우드의 별도 실행 환경 |
| 트리거 | Claude가 세션 안에서 바로 실행 | 사용자가 직접 명시적으로 입력해야 함(과금 있음) |
| 구조 | 여러 관점(finder angle)을 세션 안에서 순차/병렬 서브에이전트로 호출 → 후보 취합 → 검증 | 완전히 독립된 클라우드 에이전트 여러 개를 동시에 띄워 브랜치/PR 전체를 더 넓게 훑음 |
| 범위 | 지정한 diff (보통 `main...HEAD`) | 브랜치 전체 또는 PR 번호(`/code-review ultra <PR#>`) |
| 결과 위치 | 대화 안에 바로 표시 | GitHub PR에 리뷰 코멘트로 직접 달림 |
| 토큰/비용 | 이번 세션 토큰 예산 안에서 소비, 추가 과금 없음 | 별도 클라우드 컴퓨트 사용, **추가 과금되는 기능** |

→ 평소엔 `/code-review`로 충분. 머지 직전의 크고 중요한 PR에만 `/code-review ultra`를 추가로
돌리는 게 비용 대비 합리적.

## 3. 리뷰를 "언제" 돌릴지 — 빈도가 아니라 위험도로 정한다

"PR마다 하기엔 비효율적이니 하루 1~2번, 또는 새 세션 시작 전에 몰아서 하자"는 접근은
권장하지 않음.

- **토큰 비용 측면에서 이득이 없다**: `/code-review`는 세션 토큰 안에서 도는 거라 PR마다
  하든 몰아서 하든 총 소모량은 비슷하거나, diff가 커질수록 오히려 더 든다.
- **정확도가 떨어진다**: 리뷰 관점(finder angle) 개수는 대체로 고정인데, 몰아서 큰 diff를
  넣으면 같은 관점이 몇 배 넓은 표면을 훑어야 해서 후보 하나당 덜 꼼꼼해지고 실제 문제를
  놓칠 확률이 올라간다.
- **노출 시간이 늘어난다**: 리뷰 대기 상태로 머지/배포되면, 그 사이 진짜 버그(이번처럼 XSS)가
  방치되는 시간이 그만큼 길어진다.

### 대신 이렇게 게이팅한다

- **머지/PR 올리기 직전엔 항상 리뷰** — 시점이 아니라 "이 변경을 정말 합칠 거냐"의 문제라
  스킵하지 않는다. 대신 diff가 작으면 리뷰 자체는 몇 분 안 걸린다.
- **다음 종류는 무조건 리뷰**:
  - 로그인/인증 관련 코드
  - 사용자 입력을 화면에 렌더링하는 코드 (`innerHTML`, `dangerouslySetInnerHTML` 등)
  - 결제, API 키, 비밀번호/토큰을 다루는 코드
- **다음 종류는 가볍게 스킵 가능**:
  - 문서 수정, CSS 값 조정, 로그 문구 수정처럼 위험도가 낮은 diff

## 4. 그 밖의 이 세션 작업 원칙 (기존 메모리와 연결)

- 커밋/푸시/PR 생성은 명시적으로 요청했을 때만 실행한다 — 별개의 승인 단위로 취급.
- 보안 관련 리뷰 결과를 "정말 터지는지" 확인하고 싶을 때는 실제 앱을 건드리지 않고,
  취약한 코드 조각을 그대로 복사한 격리된 재현 페이지를 만들어 로컬에서만 검증한다
  (운영 DB/세션에 영향 없음).
